1비밀 설정 파일(.env)이 깃허브에 올라갈 수 있어요

`.env` 파일이 `.gitignore` 목록에 없습니다. 이 상태로 깃허브에 올리면 파일 안의 내용이 그대로 공개됩니다.

.env

왜 위험한가요

파일 안에 공개돼도 되는 값만 있다면 지금 당장 피해는 없어요. 하지만 결제 키나 관리자 비밀번호가 들어 있거나 나중에 추가하면, 그대로 인터넷에 공개됩니다. 남이 그 키로 요금을 쓰거나 데이터를 훔칠 수 있어요.

고치는 법 — 아래를 복사해 Cursor/Lovable에 붙여넣으세요 
`.gitignore` 파일 맨 아래에 `.env` 를 추가해줘. 그리고 이미 깃에 올라간 `.env` 가 있다면 깃 기록에서도 지우는 방법을 알려줘.

2잠금은 켰지만 열쇠가 누구에게나 맞아요

보안 정책의 조건이 'true'(항상 통과)로 되어 있습니다. (policy "anyone can read" on notes (SELECT) — using/with check (true))

supabase/migrations/001_init.sql:7

왜 위험한가요

RLS를 켜도 이 정책 때문에 사실상 아무나 통과해요. 공개 게시판처럼 일부러 연 게 아니라면 남의 데이터가 보이거나 바뀔 수 있습니다.

고치는 법 — 아래를 복사해 Cursor/Lovable에 붙여넣으세요 
이 정책의 조건 true를 'auth.uid() = user_id'처럼 로그인한 본인 것만 허용하는 조건으로 바꿔줘. 읽기(USING)와 쓰기(WITH CHECK) 둘 다 바꿔줘.

.env 파일이 깃에 올라가지 않게 .gitignore에 들어 있는지 봤어요.

⚠️
데이터 잠금(RLS) 설정확인함 · 살펴볼 것 있음

테이블을 만드는 SQL에서 2개 테이블의 잠금 설정을 읽었어요. 코드에 적힌 내용 기준이라, 실제 데이터베이스가 코드와 같은지는 따로 확인이 필요해요.

✅
서버 기능의 로그인 확인확인함 · 문제 못 찾음

서버에서 도는 코드 1개 파일을 살펴봤어요. 다른 파일에서 한꺼번에 로그인을 확인하는 구조는 놓칠 수 있어요.

➖
남의 데이터 접근 차단(본인 것만)해당 없음

모든 잠금을 건너뛰는 관리자 권한 코드는 없었어요. 이 경우 '본인 것만'은 데이터 잠금(RLS)이 맡아요.

❓
실제로 막히는지(밖에서 요청해 보기)확인 못 함

이번 점검은 앱의 데이터베이스에 요청을 보내지 않았어요. 주인이 확인된 앱에만 보내기 때문이에요. 그래서 실제로 막히는지는 알 수 없어요.

볼 수 없었던 영역은 이렇게 확인할 수 있어요

  1. AI 도구에게 물어보기

    아래 문장을 Cursor나 Lovable에 붙여 넣으면 잠금이 꺼진 테이블을 목록으로 보여 줘요.

    이 프로젝트의 Supabase 설정과 마이그레이션 파일을 보고, RLS가 꺼진 테이블과 누구에게나 열린 정책을 목록으로 보여 줘. 고치기 전에 테이블마다 누가 읽고 써야 하는지 나에게 먼저 물어봐.
  2. Supabase 대시보드에서 직접 보기

    Supabase를 쓴다면 대시보드에서 Advisors → Security Advisor를 열어 보세요. 빨간 경고가 있으면 그것부터 고치면 돼요. 무료이고 5분이면 돼요.

  3. 사람에게 맡기기

    직접 보기 어렵다면 사람이 확인해 드려요. 서면 동의를 받은 뒤 읽기 요청만 보내서 실제로 막히는지 확인해요.

🟢잘 되어 있어요 4

3잘 된 점: RLS(행 보안)가 켜져 있어요

데이터베이스에 Row Level Security를 켜는 설정이 있습니다. 로그인한 본인 데이터만 보이게 하는 핵심 잠금이에요.

4잘 된 점: 접근 정책이 설정돼 있어요

누가 무엇을 볼 수 있는지 정하는 정책(policy)이 코드에 있습니다. 잘 챙긴 부분이에요.

5잘 된 점: 서버에서 로그인을 확인해요

서버 기능에 로그인 확인(인증)이 있습니다. 화면뿐 아니라 뒷문도 지키고 있어요.

6잘 된 점: 본인 데이터만 거르는 조건이 있어요

쿼리에 '내 것만' 걸러내는 조건(user_id 등)이 보입니다. 남의 데이터 접근을 막는 좋은 습관이에요.
